# Superagent 安装引导

本技能是**安装协调流程，不是执行授权**。默认只询问和只读检查；不要在用户尚未决定工作方式、网络方案或完成准备时安装插件、改 profile、启动服务、恢复业务。依赖安装属于可单独批准的环境准备，不等于插件安装授权。一次问一个缺失问题，优先复用用户已明确给出的答案；跳过/空答案不是同意。不要因为当前 Agent 恰好在 Windows/WSL，就替用户选模式。

## 1. 必须先确定工作方式

先问：**使用哪一种工作方式？**

| 选择 | DSH/模型/数据库在哪里 | 工具和项目在哪里 | 安装来源 |
| --- | --- | --- | --- |
| A．官方默认工作方式（同侧执行） | 已确认的 DSH Host/profile | 与 DSH 同侧，按该环境的原生工具要求执行 | 代码来源按 DSH 版本选择；Desktop 0.2.2-rc.3 优先当前分支，不等于强制旧官方源码 |
| B．Windows DSH 客户端＋WSL 后端 | Windows Desktop Host/profile 管理 UI、模型和本地 SQLite | 明确的 WSL distro/user/UID/HOME，使用该用户的原生 CLI | 本 fork 的 `feature/windows-wsl-hardening`，在 WSL 构建机器版单插件 tgz |

- A 的“官方默认”只描述同侧运行形态，不代表官方产品或强制使用旧官方源码。独立 POSIX 部署的上游默认是专用 Web profile/tmux；已有 Desktop 则先确认是否沿用现有 Host/profile，不自动再开第二服务。在 WSL 里独立运行 Linux DSH 也属于 A，同 Windows Host＋WSL 工具后端 B 不同。
- **工作形态与代码来源是两个选择。** 当前已实测桌面基线为 **DSH Desktop 0.2.2-rc.3**，本分支修补版为 **0.2.0-wsl.2**。检测到该 Desktop 后，**无论选择 A 还是 B，都优先推荐当前 `feature/windows-wsl-hardening` 分支**，因为旧官方分支可能不兼容当前 Core；说明理由并让用户确认来源。用户明确坚持官方源码时，只有其 manifest/公开 API 兼容性核实后才使用；不自动降级 DSH。
- 推荐当前分支不等于所有原生平台/运行形态均已实测。A 的具体 Host/原生执行组合未验证时，先停在准备阶段列出缺口，不假称兼容、不静默转 B；B 才采用已有 Windows＋WSL 实测矩阵。不把“当前实测版本”写成“任何最新版都兼容”。
- B 不另起 Linux DSH/第二模型服务，不自动切换 WSL 默认用户、改 automount、修改 Docker 发行版，也不强制 root。
- 用户不确定时，先解释两种进程/凭据/文件边界，停在选择阶段。切换模式是迁移任务，不是在已有目录里重跑安装。

## 2. 再确认跨网需求，让用户选择

问：**模型 API、GitHub、项目代码和依赖下载是否处于不同网络？** 给出选择并等用户确认：

1. 无跨网：选定执行侧能直接访问获准服务。
2. 同机受控跨网：必须使用单位/用户批准的 VPN、代理、证书或软件镜像；用户提供准备方案。
3. 隔离网/双机或人工中转：先规划合规通道、数据范围与交接责任；本技能不自动建立分布式调度或文件/凭据同步。
4. 暂不确定：只做离线版本/路径检查，不登录、不联网诊断、不安装。

跨网不等于双机，Windows＋WSL 也不等于两个网络。读取 [网络与账号准备](references/network-and-accounts.md)，完成端点/执行侧矩阵。不要自动创建代理、VPN、SSH、端口转发、外网监听或定时任务，不关闭 TLS/签名验证；网络可达不等于允许把内部代码发给外部模型或 GitHub。

## 3. 安装前准备门禁

读取 [准备检查清单](references/preflight.md)，列出每项的 `ready / pending / unknown`、证据和由谁准备。特别提醒用户：

- 依赖和版本：选择路线要求的 DSH/Node/pnpm/Git/Python/CLI；A 按所选同侧部署核对是否需要 tmux 等，B 另核 Windows/WSL 原生工具与 Host 本地盘。
- GitHub：目标 `owner/repo`、独立 Agent **用户账号**、仓库邀请/写权限、正确执行侧的专用 CLI 与登录配置。用户自己在终端登录；不在聊天接收 Token/密码/凭据文件，不替换个人 `gh` 登录。
- 模型：选择 provider/model、费用与可发送数据范围；B 配置在 Windows Host，不把模型密钥复制进 WSL。存在 provider 配置不证明实际推理成功。
- 工作目录：源码、制品、状态数据库、部署主根、工单根和基础 clone 分开；记录用途/归属，不自动搬迁已有数据。
- 已有安装：核对 profile、包层/启用状态、历史数据、Session、来源/处理开关与备份方案。不能只凭 `running=0` 就替换。

**任一必需项为 pending/unknown：停止在准备阶段。** 给用户一份短准备清单和不含秘密的命令模板，等用户完成后再验证。批准安装依赖、创建账号、CLI 登录、网络 GET、写探针、业务试运行和创建定时巡检是不同授权；不相互推定。不要反复要求用户把已经验证过的信息再报一次。

## 4. 准备就绪后，展示唯一安装计划并确认

计划必须列出：模式/来源与 revision、目标 profile/运行侧、网络路线、依赖与额外脚本、账号/稳定 ID 与 CLI 归属、各目录、将修改的包/配置、是否新服务/重启、备份与回滚、配置/运行/来源最终状态、未验范围。

- 默认新部署保守配置：来源关闭、处理暂停、人工允许名单最小、并发 1、不自动合并。其他业务默认按已选代码版本和工作方式说明，不把旧官方版本参数套到当前分支，也不以工作方式代替能力核验。
- 已运行部署先展示当前开关，询问维护期间如何处理。**恢复原业务开关也需明确同意**；否则升级后保持暂停/来源关闭。
- 必须取得“按此计划安装/升级”的明确确认。未确认、用户正在补充问题或说“稍等”时，不安装、不改当前 profile/开关。

## 5. 严格分流执行，不混用

- **A → [默认同侧安装](references/official-default.md)**：先按 DSH 版本确认代码来源；Desktop 0.2.2-rc.3 优先本分支，但保持同侧工作方式，不注入 WSL target 或调用 WSL 机器版生成器。若经核实选择官方源码，才读取独立官方 checkout 的对应 SETUP/部署文档安装。已有 Host/profile 不重建，未验证的原生组合不直接安装。
- **B → [Windows Host＋WSL 安装](references/windows-wsl.md)**：只从已确认的当前 hardening 分支/revision 构建一个自包含机器版插件，通过目标 Windows profile 的正式插件管理器安装。不再叠“主包＋本地配置外挂”，不改 DSH 核心或手写整个 profile。

安装后先验证配置与身份，不直接接单。机器字段是否可写以当前 Core 公共 API 为准：本分支回显补丁中，部署页 stateDir/WSL 目标仅显示有效只读配置；只有三个 volatile 上限可通过 ConfigForm 保存。换工作目录、换状态库、换账号不能混为一个保存操作。

## 6. 验证与交接

分别记录：包安装/activation、配置与绑定、工具链、账号只读 GET、模型实际调用、业务闭环。`applied`、静态预演、网络可达或 `ready` 均不能替代所有其他层级；缺浏览器控制就明确未做实际视觉验收。

1. 核对真实当前 URL/profile、包版本、`application`/warnings 和重启是否完成；替换包若要求完整 Host 重启，刷新页面不能代替，不反复安装碰缓存。
2. 核对 stateDir/UID/HOME、主根/工单根、repo/account 稳定 ID、来源与处理最终状态；确认未被其他用户操作改变。
3. 静态预演不执行程序；网络 GET 和临时写探针分别获批。只读诊断不宣称物理零落盘，禁止以测试为由触发模型、工单、评论、PR、push 或 auto-merge。
4. B 的 legacy 首次绑定/目标变化要显示实际计划并确认；cutover 与 preserve、是否跳过旧事件必须讲清。清理未确认的安全 hold 不得强制清除。
5. 如需一次小业务测试或恢复接单，最后单独询问。官方建议的 hourly 检查必须单列并经用户明确请求，不能自动创建。
6. 报告通过、失败、跳过、待验收，以及匹配的制品/版本/备份位置（现场私有）。不把原始日志、机器路径、业务账号或凭据提交公开仓库。

报告完成后停止。已有非本次相关任务、其他 profile/服务和测试 VM 不应被清理；删除资源或额外改变网络需要另行授权。
